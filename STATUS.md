# Текущий статус

## Известно

- Исходные требования и dev-выборка сохранены в `data/raw/`.
- Базовое описание кейса находится в `docs/core/PROJECT.md`.
- В `research/product-materials-interim.md` заполнены пользователь и проблема, продуктовая гипотеза, основной сценарий и предварительные критерии успеха; остальные разделы остаются каркасом.
- Итоговое описание решения для финальной сдачи — `research/project-description-final.md`. Продуктовая часть — комплект из трёх материалов: `research/product-materials-final.md`, `research/product-decisions-to-implementation.md`, `research/positioning-and-scale.md`. `research/project-description-interim.md` сохранён как исторический снимок промежуточной сдачи; актуальное техническое состояние фиксируется здесь и в `solution/webapp/README.md`.
- Основной пользователь — администратор проектного офиса; менеджер проекта, руководитель операционного подразделения и пользователи пространства также просматривают рекомендации и подтверждают изменения.
- Конкурентные паттерны и модель экономики функций собраны в `research/adjacent-products-and-feature-economics.md`.
- Сценарная unit-экономика всего помощника и Excel-модель описаны в `research/unit-economics.md`; внутренние коммерческие данные MWS отсутствуют, цены и затраты фичи не подтверждены.
- Фактическая реализация разделена в `solution/` на два независимых трека: встраиваемый Widget Script и самостоятельное веб-приложение `solution/webapp/`; граница зафиксирована в `AGENTS.md` и `solution/README.md`.
- В `solution/webapp/` Change Set API сохраняет каждую draft-версию, решения пользователя, результаты действий и события в SQLite; доступны история, diff, публикация, supersede/discard и компенсирующий rollback. Выбор хранилища и правила целостности зафиксированы в ADR 0001.
- UI создаёт и публикует Change Set только через backend, который остаётся источником истины для действий и конфликтов. Локальные `engine.js`, `widget-script.js` и `launch.js` продолжают считать сопоставление сотрудников, классификацию типа проекта и план задач для итогового отчёта запуска, но эти подсказки не сохраняются и не публикуются. Отсюда расхождение: отчёт запуска считает по 30 встроенным записям, а панель — по разобранным из выгрузки.
- В набор изменений добавлено сопоставление заявки со справочником компаний из `data/raw/dev-sample.csv`: 1400 записей справочника, совпадение по ИНН, email, телефону, названию и алиасам, уровень уверенности вместо необоснованного числового score, неоднозначные и неактивные совпадения остаются человеку.
- В веб-приложении добавлен поиск возможных дублей по всему корпусу из 6800 заявок. Он требует совпадения названия проекта и хотя бы одного признака компании, предлагает ссылку `duplicate_of`, не удаляет и не объединяет исходные записи.
- Нормализация покрывает 14 полей, включая валюту, приоритет и статус. Город приводится к каноническому написанию из справочника, разворачивается транслитерация и английские экзонимы (`Tomsk` → `Томск`, `Moscow` → `Москва`); каноническое название компании берётся из справочника, что разом закрывает латиницу, город в конце названия и разнобой регистра. Телефон проверяется по телефонному плану и сохраняется в E.164; произвольный текст, маскированные номера и добавочные не превращаются в применяемые изменения. Структура email также проверяется до создания действия и использования в matching.
- Docker Compose монтирует SQLite в named volume `change-set-storage`; forward-only миграции выполняются при старте backend.
- В `solution/webapp/` реализовано интеллектуальное объяснение выбранных действий через Groq: само нажатие «AI-объяснение» является явным действием и сразу запускает анализ; вместе с результатом UI показывает фактически переданный маскированный payload. Backend валидирует structured output и сохраняет результат или ошибку с моделью и версией промпта. Без ключа детерминированный Change Set flow продолжает работать.
- Работа с полной выгрузкой реализована: backend держит snapshot из 6800 заявок, отдаёт его страницами, строит Change Set по выгрузке, публикует и откатывает относительно snapshot. Разбор идёт партиями по 100 записей, и интерфейс явно это пишет: решения по всем ~72 000 действиям не помещаются в тело запроса. Снятие ограничения требует массовой формы решений — зафиксировано в ADR 0003.
- Значения, которые правила не восстанавливают (опечатки, смешанный алфавит, сокращения — 522 города из 6800), помечаются `UNRECOGNIZED_CITY` и разбираются моделью по отдельному явному действию. Ответ проверяется локально по словарю справочника и становится обычным предложением со статусом `pending`: в записи оно попадает только при публикации. Автовызов из правила нормализации не делается — базовый сценарий обязан работать без LLM.
- AI-панель Copilot отвечает на вопросы о текущей версии и показывает, что именно было передано. Идентификаторы записей и справочника заменяются псевдонимами, контакты и ФИО маскируются; проверено, что в payload и ответе модели нет настоящих идентификаторов.
- Сквозной сценарий проверен на живом ключе Groq и модели `openai/gpt-oss-20b`. Порядок проверки стенда с ожидаемыми числами — `solution/webapp/docs/demo-check.md`.
- `GROQ_API_KEY` читается только окружением backend; `.env*` исключены из Git и Docker build context, а `make security-check` проверяет ignore-правила и tracked-файлы перед push.

## Открытые вопросы

- Какие проблемы и функции подтвердит заказчик?
- Какой UX подтверждения изменений поддерживает MWS Tables?
- Какие методы и ограничения Script Widget доступны в предоставленном пространстве?
- Как будет предоставлена эталонная разметка для проверки качества?
- Каковы реальная единица биллинга MWS, стоимость обслуживания фичи и готовность заказчиков платить за модуль?
- Какие поля заявки заказчик считает обязательными? Без этого нельзя корректно реализовать `REQUIRED_FIELD_MISSING`.
- Нужно ли проверять контрольную сумму ИНН или только формат из 10/12 цифр? Dev-выборка синтетическая, поэтому это должно быть отдельным продуктовым решением.
- Какой контракт перенесёт в backend оставшиеся локальные расчёты — сопоставление сотрудников, классификацию типа проекта и план задач с исполнителями? Пока они живут на клиенте, итоговый отчёт запуска расходится с панелью по числам.
- Какая из пяти углублённых интеллектуальных функций кейса фиксируется как заявленная? Разбор спорных значений моделью ближе всего к «LLM-проверке неоднозначных соответствий», но выбор не подтверждён.
- Нужна ли массовая форма решений («принять всё, кроме перечисленного»)? Без неё разбор идёт партиями по 100 записей.
