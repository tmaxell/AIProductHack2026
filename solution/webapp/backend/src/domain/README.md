# domain

Слой чистой доменной логики: без Fastify, без HTTP, без переменных окружения.
Функции принимают данные и возвращают данные, поэтому тестируются изолированно.

```text
domain/
├── normalize/     # правила нормализации значений, по файлу на правило
├── matching/      # сопоставление со справочником компаний
├── rules.ts       # реестр правил: поле → нормализатор + метаданные для отчёта
├── change-set.ts  # построение набора изменений из записей
├── apply.ts       # применение только подтверждённых действий
└── fingerprint.ts # отпечаток исходных данных для обнаружения конфликта
```

## Набор изменений

`buildChangeSet(records)` ничего не изменяет: он возвращает список предлагаемых
действий, замечания и отпечаток исходных данных. Каждое действие имеет
детерминированный id `<recordId>::<ruleCode>`, поэтому повторный расчёт по тем
же данным даёт тот же набор и те же идентификаторы.

`applyActions(records, changeSet, selectedIds)` применяет **только**
подтверждённые действия и не мутирует входные записи. Действие, значение
которого уже совпадает с целевым, попадает в `skipped` — повторный вызов
безопасен.

Хранилища у набора изменений пока нет: он рассчитывается заново на каждый
запрос. Версии, публикация и rollback требуют выбора персистентности, а это
решение по плану принимается отдельным ADR.

## Сопоставление со справочником

`matchCompany` сравнивает заявку с записями справочника по ИНН, email, телефону,
названию (включая алиасы и юридическое название) и городу. Все сравнения идут по
нормализованным значениям, поэтому «ИНН 77 1234 5678» и «7712345678» — одно и то же.

Уровень уверенности выводится из состава совпавших признаков и всегда
сопровождается их перечнем:

| Что совпало | Уровень |
|---|---|
| ИНН | высокий — в справочнике ИНН уникален |
| два и более признака из email, телефона, названия | высокий |
| один контактный признак: email или телефон | средний |
| название и город | средний |
| только название | низкий |

Город сам по себе совпадением не считается: признак слишком слабый и работает
только как подтверждающий.

Это **уровень, а не вероятность**. Эталонной разметки у команды нет, поэтому
числовой score был бы необоснованным: глоссарий требует калиброванной оценки,
а откалибровать её сейчас не на чем.

Автоматически не разрешаются два случая — они попадают в замечания, а не в
предложения:

- несколько записей справочника совпали одинаково хорошо — `AMBIGUOUS_COMPANY_MATCH`;
- лучшая найденная запись неактивна — `INACTIVE_COMPANY_MATCH`.

## Отличия от прежней реализации на фронтенде

Логика перенесена из `frontend/public/widget-script.js`. При переносе исправлены
три дефекта, воспроизводившиеся на dev-выборке:

| Было | Стало |
|---|---|
| `Г. Сочи` → `. Сочи`, `Гагарин` → `агарин` | префикс `г` снимается только с точкой или пробелом |
| `31.02.2027` → `2027-03-03` молча | ошибка `IMPOSSIBLE_DATE`, изменение не предлагается |
| `2027-01-01T00:00:00Z` считалось нормализованным | приводится к `2027-01-01` |

Неиспользовавшиеся `normalizeCompany` и `normalizeProjectName` не переносились:
они всегда возвращали `changed: true` и дали бы неидемпотентные предложения.

Граница: сюда **не** переносится код Widget Script для реальных MWS Tables
(`solution/src/`). Это отдельный трек, см. [`../../../README.md`](../../../README.md).
