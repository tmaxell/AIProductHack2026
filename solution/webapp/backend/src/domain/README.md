# domain

Слой чистой доменной логики: без Fastify, без HTTP, без переменных окружения.
Функции принимают данные и возвращают данные, поэтому тестируются изолированно.

```text
domain/
├── normalize/     # правила нормализации значений, по файлу на правило
├── matching/      # сопоставление со справочником и поиск дублей заявок
├── rules.ts       # реестр правил: поле → нормализатор + метаданные для отчёта
├── change-set.ts  # построение набора изменений из записей
├── apply.ts       # применение только подтверждённых действий
└── fingerprint.ts # отпечаток исходных данных для обнаружения конфликта
```

## Набор изменений

`buildChangeSet(records)` ничего не изменяет: он возвращает список предлагаемых
действий, замечания и отпечаток исходных данных. Каждое действие имеет
детерминированный id `<recordId>::<ruleCode>`, поэтому повторный расчёт по тем
же данным даёт тот же набор и те же идентификаторы.

Значение с блокирующей ошибкой остаётся в замечаниях, но не превращается в
применяемое действие. Невалидные ИНН, email и телефоны не используются как
ключи сопоставления; маскированный телефон и телефон с добавочным также не
участвуют в matching до ручного разрешения.

`applyActions(records, changeSet, selectedIds)` применяет **только**
подтверждённые действия и не мутирует входные записи. Действие, значение
которого уже совпадает с целевым, попадает в `skipped` — повторный вызов
безопасен.

Хранилища у набора изменений пока нет: он рассчитывается заново на каждый
запрос. Версии, публикация и rollback требуют выбора персистентности, а это
решение по плану принимается отдельным ADR.

## Что нормализуется в значении, а что только при сравнении

В значении чинится форма записи: регистр email, формат телефона и дат, разряды
и валюта бюджета, лишние пробелы, префикс «ИНН», префикс «г.» у города,
словарные значения валюты, приоритета и статуса.

Телефон разбирается по метаданным телефонных планов `libphonenumber-js/max`:
номер без международного префикса считается российским, международный номер
должен содержать код страны, а результат сохраняется в E.164. Произвольные
буквы не вырезаются. Маскированные номера и номера с добавочным сохраняются без
изменений и требуют review; добавочный не отбрасывается, пока для него нет
отдельного поля.

Только при сравнении сводятся:

- **«ё» к «е»** — «Королёв» и «Королев» должны совпасть, но выбрасывать букву
  из данных нельзя. Так же устроено в виджет-треке (`normalizeYoAndCase`);
- **организационно-правовая форма** — «ООО Ромашка» и «Ромашка» совпадают, но
  в значении ОПФ остаётся: «ООО Ромашка» и «АО Ромашка» — разные юридические
  лица, а справочник хранит полное и короткое название отдельными полями.

Регистр названия компании не трогается вовсе: «МТС» и «ИТ-Град» превратились бы
в «Мтс» и «Ит-Град». Каноническое написание должно приходить из справочника
после сопоставления, а не из эвристики.

## Словарные значения

Целевые значения не выдуманы, а взяты из самого набора данных:

| Правило | Словарь | Откуда взят |
|---|---|---|
| Валюта | `RUB` | ISO 4217; `RUB` уже встречается наравне с `RUR`, `руб.`, `₽`, `рубли` |
| Приоритет | Критический, Высокий, Средний, Низкий | шкала полей `task_priority` и `template_default_priority` того же набора |
| Статус | Новая, На проверке, Черновик | написания, которые уже есть в данных |

21 вариант приоритета в заявках раскладывается по четырём значениям без
остатка. Незнакомое значение не меняется, а помечается предупреждением:
`CURRENCY_UNKNOWN`, `PRIORITY_UNRECOGNIZED`, `STATUS_UNRECOGNIZED`.

## Сопоставление со справочником

`matchCompany` сравнивает заявку с записями справочника по ИНН, email, телефону,
названию (включая алиасы и юридическое название) и городу. Все сравнения идут по
нормализованным значениям, поэтому «ИНН 77 1234 5678» и «7712345678» — одно и то же.

Уровень уверенности выводится из состава совпавших признаков и всегда
сопровождается их перечнем:

| Что совпало | Уровень |
|---|---|
| ИНН | высокий — в справочнике ИНН уникален |
| два и более признака из email, телефона, названия | высокий |
| один контактный признак: email или телефон | средний |
| название и город | средний |
| только название | низкий |

Город сам по себе совпадением не считается: признак слишком слабый и работает
только как подтверждающий.

Это **уровень, а не вероятность**. Эталонной разметки у команды нет, поэтому
числовой score был бы необоснованным: глоссарий требует калиброванной оценки,
а откалибровать её сейчас не на чем.

Автоматически не разрешаются два случая — они попадают в замечания, а не в
предложения:

- несколько записей справочника совпали одинаково хорошо — `AMBIGUOUS_COMPANY_MATCH`;
- лучшая найденная запись неактивна — `INACTIVE_COMPANY_MATCH`.

## Поиск дублей заявок

Дубли ищутся **по всей таблице заявок**, а не внутри выбранного набора:
заявка-оригинал может не попасть в выбор пользователя. Корпус загружается из
того же набора данных, что и справочник.

Условие: совпало нормализованное название проекта **и хотя бы один признак
компании**. Одного названия проекта мало — «Внедрение CRM» встречается у
разных компаний.

| Что совпало вдобавок к названию проекта | Уровень |
|---|---|
| ИНН компании | высокий |
| название компании | высокий |
| только email или телефон | средний |

Оригиналом считается запись с наименьшим `row_id` в группе — выбор
детерминирован, повторный запуск даёт тот же результат. Сама запись-оригинал
предложения не получает. Исходные записи не удаляются и не объединяются:
предлагается только проставить ссылку в поле `duplicate_of`, как того требует
ограничение кейса «удаление исходных записей не требуется».

Сравнение идёт по тем же ключам, что и сопоставление: сведение «ё», снятие
ОПФ, нормализованные ИНН, email и телефон. Поэтому «ООО «Орбита Логистика»» и
«ооо «орбита логистика»» с «партнёров» и «партнеров» попадают в одну группу.

## Отличия от прежней реализации на фронтенде

Логика перенесена из `frontend/public/widget-script.js`. При переносе исправлены
три дефекта, воспроизводившиеся на dev-выборке:

| Было | Стало |
|---|---|
| `Г. Сочи` → `. Сочи`, `Гагарин` → `агарин` | префикс `г` снимается только с точкой или пробелом |
| `31.02.2027` → `2027-03-03` молча | ошибка `IMPOSSIBLE_DATE`, изменение не предлагается |
| `2027-01-01T00:00:00Z` считалось нормализованным | приводится к `2027-01-01` |

Неиспользовавшиеся `normalizeCompany` и `normalizeProjectName` не переносились:
они всегда возвращали `changed: true` и дали бы неидемпотентные предложения.

Граница: сюда **не** переносится код Widget Script для реальных MWS Tables
(`solution/src/`). Это отдельный трек, см. [`../../../README.md`](../../../README.md).
