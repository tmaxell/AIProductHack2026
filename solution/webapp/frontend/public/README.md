# Frontend веб-приложения Project Launch Copilot

Демонстрационный фронтенд: оболочка в визуальной грамматике MWS Tables и панель
виджета, которая проверяет заявки **реальным движком** (`engine.js` — перенос
`normalize.js`, `match.js` (дедуп + сопоставление со справочниками) и
`classify.js` (тип проекта + приоритет) из `solution/src/lib/`, ветка
`feature/add_mvp_solution`) и достраивает поверх него то, чего нет даже там —
задачи по шаблону, назначение исполнителей и итоговый отчёт запуска (`launch.js`,
спроектировано заново, см. его шапку).

Это mock, а не установленный Widget Script. Оболочка воспроизводит пропорции и
визуальный язык платформы, но не является её точной копией.

Это **не** решение, встраиваемое в реальные MWS Tables. Тот трек живёт отдельно,
граница описана в [`solution/README.md`](../../../README.md). Движок в
`engine.js` физически скопирован оттуда (не импортирован), чтобы этот фронтенд
демонстрировал реальные алгоритмы без нарушения границы сборки треков — при
любом изменении `solution/src/lib/` копию нужно обновлять вручную.

## Запуск

Штатный способ — весь стек веб-приложения в Docker, см.
[`solution/webapp/README.md`](../../README.md):

```bash
cd solution/webapp && make up
```

Только эту статику, без backend и без Docker, можно поднять любым статическим
сервером из текущего каталога — данные и логика подключаются обычными `<script>`:

```bash
python3 -m http.server 8088 --bind 127.0.0.1
```

## Файлы

| Файл | Назначение |
|------|------------|
| `index.html` | Разметка оболочки, панели виджета, трёх модалок (отчёт, настройки, итоговый запуск) и набор inline SVG-иконок |
| `styles.css` | Визуальная система: токены, оболочка, таблица, состояния виджета |
| `app.js` | Presentation layer: рендер таблицы, состояния виджета, область запуска, выбор полей, отчёт, применение и откат, итоговый отчёт запуска |
| `engine.js` | **Реальный движок** — нормализация, дедуп + сопоставление со справочниками, классификация, аномалии, приоритет (см. шапку файла — там же список того, что сознательно не перенесено и почему) |
| `launch.js` | Задачи по шаблону + round-robin назначение исполнителей + итоговый план запуска — **новая логика**, этого нет ни в `solution/src/lib/`, ни где-либо ещё (см. шапку файла) |
| `widget-script.js` | Адаптер между `engine.js`/`launch.js` и плоской схемой строки этого мока (`window.LPC`) |
| `data.js` | 30 записей типа APPLICATION из `data/raw/dev-sample.csv` |
| `companies.js` / `employees.js` / `templates.js` | Справочники Компаний (1400) / Сотрудников (240) / Шаблонов задач (360, 12 типов) — **реальные записи** `COMPANY_REFERENCE`/`EMPLOYEE`/`TASK_TEMPLATE` из той же `data/raw/dev-sample.csv`, не выдуманные |

## Что действительно работает

Интерактивны только перечисленные элементы. Остальная оболочка — проводник, rail,
кнопки вида в toolbar — статична и намеренно не выглядит кликабельной.

- **Поиск** в toolbar — фильтрует таблицу по названию проекта, компании, городу,
  ИНН, идентификатору заявки и email заявителя.
- **Чекбоксы строк** и чекбокс в шапке — задают **область запуска**: если что-то
  отмечено, проверка идёт только по отмеченным записям; если нет — по всей
  таблице.
- **Настройки проверки** (кнопка в панели виджета ИЛИ иконка 👁 в тулбаре — обе
  ведут в одну модалку) — область запуска + список полей для анализа (все поля,
  которые реально читает движок, включая те, что не показаны отдельной колонкой
  в гриде). Снятая галка реально исключает поле из движка на следующем прогоне
  (нормализация, дедуп, сопоставление, классификация, аномалии), а не просто
  прячет колонку с экрана — если что-то выглядит странно после прогона, баннер
  «⛔ Исключено из анализа» виден во всех состояниях виджета с кнопкой
  «Включить все поля».
- **Проверить данные** — прогоняет всю цепочку по текущей области запуска и
  текущему набору включённых полей: нормализация → дедуп заявок → сопоставление
  с Компаниями/Сотрудниками → классификация типа/приоритета → проверка аномалий.
- **Посмотреть изменения** — отчёт по правилам (14 страниц, «Заявка / Было /
  Стало», у «Стало» во всплывающей подсказке — уверенность движка).
- **Применить все N** — применяет все предложенные изменения к данным в памяти.
- **Отменить изменения** — возвращает исходные значения.
- **Итоговый отчёт запуска** (ссылка в панели результата) — сводка (готовность,
  сколько заявок получили план задач, сколько задач сгенерировано/назначено) +
  таблица по заявкам: компания, тип проекта (с пометкой «черновик», если
  классификация ниже авто-порога), готовность, раскрывающийся список задач с
  назначенным исполнителем на каждую.
- **Свернуть панель виджета** и вернуть её вертикальной кнопкой у правого края.
- Модалки закрываются по Escape; Tab и Shift+Tab не выходят за их пределы.

## Правила проверки

14 правил нормализации/дедупа/сопоставления/классификации, по одному на страницу
отчёта. Числа ниже — фактический результат на всех 30 записях без ограничений
области/полей (после первого «Проверить данные»).

| Правило | Что делает | Изменений |
|---------|------------|-----------|
| Email компании / заявителя | нижний регистр, удаление пробелов и `mailto:` | 27 / 19 |
| Телефон компании / заявителя | единый формат `+7…` | 24 / 24 |
| ИНН компании | удаление префикса «ИНН» и пробелов | 16 |
| Город | нормализация регистра/пробелов, сверка со справочником выборки | 11 |
| Название компании | снятие организационно-правовой формы и кавычек | 22 |
| ФИО заявителя | единый регистр (включая слитные инициалы «Ю.Д.») | 14 |
| Бюджет / Валюта | очистка валюты, `млн`/`тыс.` в число / код ISO | 24 / 27 |
| Дата начала / окончания | формат `ГГГГ-ММ-ДД` | 27 / 24 |
| Приоритет | словарь приоритетов (P1..P4, рус/eng, 1..4) | 18 |
| Дубли заявок | union-find по компании/контактам/содержанию | 0 на этой выборке* |
| **Сопоставление с компанией** | поиск в справочнике по ИНН/email/телефону/названию/городу | **27** (+1 неоднозначно) |
| Сопоставление с сотрудником | то же по email/телефону/ФИО заявителя | 0** |
| Тип проекта | сходство названия с 12 каноническими шаблонами | 0*** (9 — ручной разбор) |

Итого 304 предложения (на область "вся таблица"). Готовность к запуску:
**25 из 30 (83%)** — включает реальную проверку «компания найдена и
подтверждена» (`NO_COMPANY_MATCH`), поэтому ниже, чем было до сопоставления
со справочниками (93%) — это честнее, не оптимистичнее.

\* В этих 30 записях дублей нет по дизайну выборки — алгоритм проверен отдельно
на синтетической паре записей с одинаковым `application_id`.

\*\* Сотрудники и заявители — разные синтетические популяции в этом датасете
(email на разных доменах), совпадений почти нет — это честный результат, не баг.

\*\*\* Формула классификации — `nameSim×0.5 + roleOverlap×0.25 + skillOverlap×0.25`.
В `data.js` нет `required_roles_raw`/`required_skills_raw`, поэтому
`roleOverlap`/`skillOverlap` всегда 0, а максимально достижимый score — 0.5 при
авто-пороге 0.6: авто-классификация здесь структурно недостижима. Правило
`NO_CLASSIFICATION` сознательно не включено в аномалии (иначе оно ложно
блокировало бы 100% заявок) — сама классификация всё равно считается честно и
видна в отчёте/итоговом плане запуска как «черновик».

Повторный запуск после применения предлагает 0 изменений: сценарий идемпотентен
(проверено 3 прогона подряд, включая связи с компаниями и дедуп).

## Итоговый отчёт запуска (Milestones 8-10)

Полностью новая логика (`launch.js`) — этого нет даже в `solution/src/lib/`
(там Milestones 8-11 не реализованы). Спроектирована по тем же принципам, что
заявлены в `solution/PLAN.md`: задачи — простой перенос шаблона без ML,
назначение исполнителей — **только round-robin** (по кругу среди активных
сотрудников с подходящей ролью), без учёта загрузки/навыков/отпусков.

На всех 30 записях: 9 заявок получают план (тип определён хотя бы
предварительно, score ≥ 0.3), 270 задач сгенерировано, все 270 назначены
исполнителем (роли из справочника Сотрудников полностью покрывают роли,
требуемые шаблонами).

## Чего пока нет

- Поштучный accept/reject предложений — только массовое применение (в отличие
  от реального Widget Script, где неоднозначные случаи разбираются по одному).
- Несуществующая календарная дата (`31.02.2027`) молча превращается в
  соседнюю — движок не валидирует календарь, только формат.
- Реальные Task/Project-записи не создаются — итоговый отчёт запуска строит
  план **в памяти вкладки** для просмотра, не пишет ничего в датасет (как и всё
  остальное в этом мок-фронте).

## Куда переезжает логика

`widget-script.js` не зависит от DOM и экспортирует функции через `window.LPC`.
Контракт будущего эндпоинта уже зафиксирован в
[`contracts/validation.ts`](../../backend/src/contracts/validation.ts), а
`POST /api/v1/validation/runs` до переноса честно отвечает `501`. Перенос в
backend (`solution/webapp/backend/src/domain/`) этим изменением не сделан —
только сама логика на фронтенде стала настоящей вместо фейковой.

`data.js`/`companies.js`/`employees.js`/`templates.js` — временный источник
данных; после переноса записи будут приходить из backend.
