# ADR 0003: анализ полной выгрузки и серверная пагинация действий

- Статус: принято к реализации
- Дата: 2026-09-06

## Контекст

В `dev-sample.csv` находятся 6800 заявок, но текущий frontend загружает только
30 демонстрационных строк. Backend использует полный корпус только для поиска
дублей. Если просто передать все заявки и действия в браузер, один HTTP-ответ и
DOM будут содержать десятки тысяч объектов; публикация, выбор решений и
повторный запуск станут медленными и хрупкими.

Полнота анализа и размер страницы просмотра — разные параметры. Все записи
должны участвовать в расчёте, но пользователь может просматривать изменения
порциями.

## Решение

### Snapshot полной выгрузки

Backend загружает все записи `record_type = APPLICATION` в нормализованный
`SourceRecord`-snapshot и вычисляет его fingerprint. Change Set ссылается на
snapshot и хранит источник `dataset`, а не принимает тысячи строк из браузера.
Snapshot содержит версию схемы, путь/идентификатор источника, число записей,
fingerprint и время чтения.

Повторный анализ создаёт новую версию Change Set. Публикация сверяет исходный
snapshot с актуальным fingerprint; несовпадение использует существующий
механизм конфликта и требует нового анализа.

### Выполнение

Для текущих 6800 заявок допустим синхронный расчёт внутри backend при
подтверждённом профилировании. Целевой контракт асинхронный:

1. `POST /dataset-snapshots/current/change-sets` возвращает `202` и operation id;
2. backend анализирует все записи пакетами, но формирует один Change Set;
3. `GET /operations/:id` возвращает progress, итоговый change set id или ошибку;
4. незавершённая операция не публикуется и безопасно повторяется по
   idempotency key.

Пакет вычисления не является страницей UI: matching и поиск дублей используют
весь snapshot, поэтому границы пакетов не меняют результат.

### Чтение изменений

Метаданные версии возвращаются отдельно от действий. Действия читаются
серверными страницами:

```text
GET /change-sets/:id/actions?cursor=…&limit=50
    &ruleCode=…&decision=…&result=…&recordQuery=…
```

Ответ содержит `items`, `nextCursor`, `total`, а также агрегаты по правилам,
решениям, результатам и severity. Cursor строится из неизменяемых `position/id`,
а не из offset, поэтому сохранение решения не переставляет элементы между
страницами.

UI показывает 50 изменений на странице, фильтры и общий прогресс решений.
Решение по строке сохраняется сразу. Массовое решение по фильтру передаёт сам
фильтр и fingerprint выборки; backend записывает событие с числом затронутых
действий. Публикация применяет только сохранённые `accepted` и не доверяет
локальному состоянию страницы.

### Публикация и результат

Backend применяет принятые действия пакетами к snapshot, но сохраняет результат
каждого действия существующей моделью `pending/applied/skipped/conflict/failed`.
Повтор операции продолжает незавершённые пакеты и не выполняет успешные
повторно. UI получает агрегаты и страницы результатов, а не весь изменённый
набор одним ответом. Экспорт результата формируется отдельным потоковым файлом
или адаптером MWS Tables.

## AI-объяснение полной выгрузки

Полную выгрузку и все действия нельзя безусловно помещать в один Groq prompt.
Backend сначала детерминированно агрегирует **все** действия и issues:

- количество записей и изменений;
- распределение по правилам, severity, confidence и решениям;
- блокирующие противоречия и неоднозначные matching;
- число затронутых записей и долю готовности;
- fingerprint агрегата.

Groq получает этот полный агрегат и ограниченную репрезентативную выборку
маскированных примеров по каждому типу риска. В сохранённом результате явно
фиксируются `totalActions`, `aggregatedActions`, `sampledActions` и стратегия
выборки. Поэтому текст относится ко всей выгрузке по агрегатам, но не выдаёт
примеры за полный корпус.

Если понадобится построчное семантическое чтение всех действий, используется
map/reduce: стабильные chunks → структурированные частичные выводы → один
структурированный итог. Это отдельный дорогой режим с показом числа вызовов и
оценки объёма до запуска; он не нужен для базового объяснения.

## Этапы внедрения

1. Расширить `Dataset` полными `SourceRecord` и metadata snapshot.
2. Добавить source type/fingerprint и облегчённый DTO версии.
3. Добавить cursor API действий и агрегаты; перевести список версий и отчёт.
4. Добавить создание Change Set из текущего snapshot и progress operation.
5. Добавить массовые решения по фильтру и пакетную публикацию.
6. Перевести Groq payload на полный агрегат плюс bounded sample.
7. Профилировать 6800 заявок, проверить restart/resume и UI smoke.

## Инварианты

- анализируется вся выгрузка, а не только текущая страница;
- pagination не влияет на matching, дубли или fingerprint;
- backend остаётся источником решений и результатов;
- frontend не хранит полный snapshot и не отправляет его обратно;
- LLM не получает секрет, весь необработанный экспорт или право публикации;
- старый request-based Change Set остаётся совместимым на время миграции UI.
