# ADR 0001: локальная персистентность версий Change Set

- Статус: принято
- Дата: 2026-09-06
- Область: самостоятельное веб-приложение `solution/webapp/`

## Контекст

Текущий Change Set API уже строит preview, возвращает детерминированные действия,
поддерживает выборочное применение, проверяет `sourceFingerprint` и безопасно
пропускает уже применённые значения. Однако черновик пересчитывается на каждый
запрос, решения пользователя и результаты применения не сохраняются, а история и
rollback существуют только в памяти страницы.

Приложение запускается локально через Docker Compose, не имеет отдельной
авторизации и не рассчитано на промышленную многопользовательскую нагрузку.
Backend должен оставаться единственным источником истины для сохраняемых и
публикуемых действий, пока расширенный frontend-сценарий из `engine.js` и
`launch.js` постепенно переносится за HTTP API.

## Решение

Используем SQLite-файл, принадлежащий backend, и монтируем каталог базы как
именованный Docker volume. Доступ к SQLite скрыт за интерфейсом репозитория;
доменные функции построения preview и выборочного применения остаются
независимыми от хранилища.

Причины выбора:

- транзакции, ограничения и индексы нужны для неизменяемой истории и
  идемпотентной публикации;
- один локальный файл соответствует текущей модели развёртывания и не добавляет
  отдельный сервис с учётными данными;
- WAL и короткие транзакции достаточны для одного экземпляра backend;
- схема и репозиторий оставляют возможность заменить адаптер на PostgreSQL,
  если появятся несколько экземпляров backend или подтверждённая совместная
  работа пользователей.

Не используем JSON-файлы: у них нет штатных транзакций, ограничений ссылочной
целостности и безопасного восстановления после частичной записи. Не выбираем
PostgreSQL сейчас: для локального demo это лишний контейнер и эксплуатационный
контур без подтверждённой потребности.

## Модель данных

`change_sets` хранит одну неизменяемую версию:

- `id`, `sequence` — стабильный идентификатор и человекочитаемый номер версии;
- `status` — `draft`, `published`, `superseded` или `discarded`;
- `source_fingerprint`, `source_records_json` — база preview и снимок исходных
  записей, необходимые для diff и проверки публикации;
- `published_records_json` — сохранённый результат для идемпотентного ответа на
  повторную публикацию;
- `issues_json`, `summary_json` — результат анализа на момент создания;
- `parent_id` — предыдущая версия при повторном анализе;
- `rollback_of_id` — опубликованная версия, для которой создан компенсирующий
  draft;
- `created_at`, `updated_at`, `published_at`.

`change_set_actions` хранит действия версии:

- полный снимок действия `before → after`, rule metadata, confidence и evidence;
- `decision`: `pending`, `accepted`, `rejected`;
- необязательное `edited_after` для явно отредактированного пользователем
  целевого значения;
- `result`: `pending`, `applied`, `skipped`, `conflict`, `failed`;
- `result_message`, `executed_at`.

`change_set_events` — append-only журнал создания, изменения решения,
публикации, конфликта, создания rollback и discard. Payload хранится JSON и не
заменяет нормализованные поля состояния.

Идентификатор действия уникален внутри версии. В rollback-draft идентификатор
получает суффикс `::rollback::<source version id>`, чтобы обратное действие не
смешивалось с исходным при повторных запросах.

## Миграции

Backend на старте выполняет пронумерованные SQL-миграции в одной транзакции и
фиксирует их в `schema_migrations(version, applied_at)`. Миграции только
продвигаются вперёд и должны быть идемпотентны на уровне номера версии. Ошибка
миграции блокирует старт приложения: работа на частично известной схеме опаснее
недоступности demo.

Первая миграция создаёт три таблицы, внешние ключи и индексы по статусу,
времени создания и связям версий. Изменение JSON-формата, которое нельзя читать
старым кодом, требует новой миграции данных, а не условной логики в маршруте.

## Жизненный цикл

```text
draft ──publish──> published ──new publish──> superseded
  │                    │
  └──discard──────────> discarded
                       │
                       └──rollback request──> rollback draft ──publish──> published
```

- Создание preview всегда сохраняет новый `draft`; предыдущая версия не
  перезаписывается. `parent_id` связывает последовательные анализы.
- Только `draft` допускает изменение решений и `edited_after`.
- `published`, `superseded` и `discarded` неизменяемы, кроме перехода
  `published → superseded`, выполняемого транзакционно при публикации следующей
  версии.
- Публикация применяет только действия с решением `accepted`; `pending` и
  `rejected` остаются в истории, но не исполняются.
- Повторная публикация уже опубликованной версии возвращает сохранённый
  результат и не выполняет действия повторно.
- При несовпадении fingerprint публикация не меняет данные или статус версии,
  записывает событие конфликта и возвращает конфликт вызывающей стороне.
- Частичный результат каждого действия фиксируется до безопасного повтора.
  Для текущего атомарного адаптера данных публикация фиксирует результаты и
  статус одной транзакцией. Будущие внешние адаптеры повторяют только действия
  без финального результата `applied`/`skipped`.
- Draft без действий может быть опубликован как зафиксированное решение «без
  изменений»; это сохраняет аудит пользовательского решения.

## Сравнение версий

API сравнивает снимки действий по логическому ключу `recordId + field +
ruleCode`, а не по порядку массива. Результат содержит `added`, `removed` и
`changed`; изменением считаются различия `before`, эффективного `after`,
решения или результата. Сравнение не пересчитывает доменные правила и потому
воспроизводимо для старых версий.

## Компенсирующий rollback

Rollback не переписывает историю и не восстанавливает всю таблицу. Для каждого
успешно применённого действия опубликованной версии backend создаёт новый draft
с `before = исходное after` и `after = исходное before`.

Правила:

- rollback разрешён только для `published` или `superseded` версии;
- создание rollback повторяется идемпотентно: для одной исходной версии может
  существовать только один активный rollback-draft; повтор возвращает его;
- обратные действия изначально `pending` и требуют preview и явного принятия;
- публикация rollback использует обычную fingerprint-проверку по текущим
  записям;
- дополнительно каждое обратное действие применимо, только если текущее значение
  равно значению, записанному исходной публикацией. Иначе действие получает
  `conflict`, а публикация блокируется без перезаписи чужого изменения;
- уже возвращённое к `before` значение получает `skipped`, поэтому повторная
  публикация/доставка безопасна;
- rollback опубликованного rollback создаёт ещё один компенсирующий draft, а не
  удаляет предыдущие события.

## API и граница источника истины

Версионированные маршруты работают по идентификатору сохранённой версии:

- создать и перечислить версии;
- получить версию и историю;
- сохранить решения/редактирование draft;
- сравнить две версии;
- опубликовать draft;
- создать rollback-draft;
- discard draft.

Клиент передаёт актуальные записи при создании и публикации, пока нет реального
адаптера MWS Tables. Backend строит и хранит действия, проверяет конфликт,
применяет их и сохраняет результаты. Данные `_validationChanges` из
`engine.js`/`launch.js` не являются допустимым payload для публикации.

`POST /change-sets` теперь создаёт сохранённый draft. Старый
`POST /change-sets/apply` временно сохранён как deprecated stateless-контракт и
использует те же доменные функции; UI версий использует только персистентные
маршруты.

## Последствия и ограничения

- Named volume переживает пересоздание контейнера; `docker compose down -v`
  удаляет локальную историю явно.
- Резервное копирование пока равно копированию SQLite-файла при остановленном
  backend или через штатный SQLite backup; отдельный UI для backup вне scope.
- Один writable backend instance — осознанное ограничение. Горизонтальное
  масштабирование требует серверной БД и распределённой блокировки публикации.
- Снимки записей и действий увеличивают размер файла, но обеспечивают аудит и
  воспроизводимый diff; политика retention пока не вводится.
