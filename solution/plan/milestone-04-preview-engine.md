# Milestone 4 — движок preview/apply

Статус: локально, через mock-SDK.

## Зачем

Это центральный, общий для всех остальных модулей механизм: любое предложенное изменение (нормализация, связь, аномалия-подтверждение) проходит через одну и ту же процедуру «показать было→станет → спросить подтверждение → применить батчем», а не свою для каждого модуля.

## Сквозная форма `Action`

Все модули (normalize, match, classify, anomalies) производят массивы объектов этой формы — это единственный формат, который понимает preview-движок:

```ts
{
  recordId: string,     // id записи, которую меняем
  table: string,         // "applications" | "companies" | "employees" | "tasks" | "projects" — логическое имя из CopilotConfig.tables
  field: string,          // логическая роль поля (см. таблицу ролей в Milestone 2), не сырой fieldId
  from: any,              // ТЕКУЩЕЕ ЗНАЧЕНИЕ ПОЛЯ-НАЗНАЧЕНИЯ (то, что будет перезаписано) — именно
                           // сравнение from===to и есть идемпотентность движка (см. "Что делает" п.7)
  displayFrom?: any,       // опционально: сырое значение-источник для читаемости колонки "Было" в preview,
                           // когда оно отличается от from (типичный случай — normalize: from = normalized_*
                           // поле, изначально пустое, displayFrom = *_raw значение, которое реально видит человек)
  to: any,                // предлагаемое значение
  changed: boolean,
  confidence: number,     // 0..1
  reason: string,
  kind: "normalize" | "link" | "classify" | "anomaly-ack"
}
```

**Важно (найдено и исправлено при тестировании Milestone 3/4):** `from` — это НЕ сырое значение-источник, а текущее значение поля, которое действие собирается перезаписать. Для `kind:"normalize"` источник (`*_raw`) и назначение (`normalized_*`) — разные поля, поэтому `from` = текущее `normalized_*` (пусто при первом прогоне, равно `to` после применения), а `*_raw` идёт отдельным полем `displayFrom` только для отображения. Для `kind:"link"`/`"classify"` источника-дубликата нет — `from` = текущее значение самого поля-связи/классификации, `displayFrom` не нужен. Если бы `from` было сырым значением всегда, идемпотентность бы никогда не срабатывала (raw-поля не перезаписываются, поэтому `from !== to` было бы истинно вечно) — именно так проявлялся баг на реальном прогоне 6800 заявок, пока не был найден.

## Вход

- Массив `Action[]` (собранный из normalize.js/match.js/classify.js на предыдущих шагах прогона). Действия с одинаковым `(table, recordId, field)` внутри ручной группы — это варианты **одного и того же** неоднозначного случая (`match.js#optionIndex`, Milestone 5, US11 в `research/user-stories.md`), а не независимые действия.
- `sdk` (`input`, `output`).
- `config.thresholds` (`matchAuto`, `matchManualLow`, `matchTopK`, `classifyAuto` — используются только для `kind:"link"`/`"classify"`; `kind:"normalize"` обычно все выше базового порога показа, т.к. правила детерминированные).

## Что делает

1. Делит `Action[]` на **авто** (`confidence >= порог`, ровно один `Action` на запись) и **ручные** (ниже порога, но выше минимального порога показа — совсем низкую уверенность не показываем вообще, см. Milestone 3/5).
2. Печатает авто-группу как обычную пронумерованную таблицу: `# | Таблица | Поле | Было | Станет | Причина | Уверенность`. Ручную группу печатает **сгруппированной по записи** с буквенным суффиксом на вариант: `12a`, `12b`, `12c` — все строки с номером `12` относятся к одной неоднозначной записи, каждая буква — один из до `matchTopK` вариантов на выбор (US11).
3. Спрашивает подтверждение раздельно: для авто-группы — `input.textAsync("Какие строки применить? 'all' / 'none' / номера через запятую, например 1,3,5-8")`, дефолт при пустом вводе — `all`; для ручной группы — `input.textAsync("Для каждой неоднозначной строки укажите вариант (например 12b,15a) или не упоминайте номер, чтобы пропустить")`, без дефолта — непомянутая группа просто пропускается (ни один вариант не применяется).
4. Парсит ответ авто-группы в набор индексов (поддержка диапазонов `5-8` и списков `1,3,5-8`); ответ ручной группы — в набор пар «номер группы + буква варианта», каждая пара разрешается ровно в один `Action` этой группы.
5. Группирует подтверждённые `Action` по `(table, recordId)` в один вызов `updateRecordsAsync` на таблицу (батчами, размер батча — see Milestone A по факту лимитов).
6. Для `kind:"normalize"` дополнительно обновляет `_processed_hash` (хэш от текущих `*_raw` значений записи) и `_last_run_id` у затронутых заявок.
7. **Идемпотентность на этом уровне**: перед показом действие исключается из списка вовсе, если `from === to` (уже применено) — тогда предложений не будет и на повторном прогоне.

## Критерий готовности

- Повторный вызов `runPreviewCycle` с тем же исходным `Action[]`, но **после** того как эти действия уже применены на предыдущем прогоне, возвращает пустые группы (нечего показывать, `applied: []`) — потому что `from !== to` больше не выполняется.
- Парсер диапазонов (`"1,3,5-8"`) покрыт юнит-тестом на границы (пустая строка, `"all"`, `"none"`, некорректный ввод — не должен падать, должен переспросить или трактовать как `"none"` с понятным сообщением).
- Парсер выбора вариантов (`"12b,15a"`) покрыт тестом: номер без буквы для группы с несколькими вариантами — понятная ошибка, а не тихий выбор первого попавшегося; номер, упомянутый дважды с разными буквами — тоже понятная ошибка (одна запись не может получить два разных варианта одновременно).
- Батч на несколько записей одной таблицы уходит одним вызовом `updateRecordsAsync`, а не N отдельными.

## Демонстрация (обязательный шаг перед переходом к следующему milestone)

Полный интерактивный прогон `run-local.js` на подвыборке заявок (реальные предложения нормализации из Milestone 3, поданные через preview): видно авто-таблицу, отвечаем `all`/номерами, видно применённые изменения — либо в дампе `local-seed.json` после прогона, либо через `--html` в браузере (реальные ячейки «Заявок» поменялись). Второй запуск подряд — предложений по уже изменённым записям больше нет.
