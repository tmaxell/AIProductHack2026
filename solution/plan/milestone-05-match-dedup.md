# Milestone 5 — дедуп и сопоставление со справочниками

Статус: локально, чистые функции + подключение к preview-движку (Milestone 4).

## Зачем

Основная «грязь» в данных — не дубли самих заявок (их мало, 23 из 6777 по `application_id_raw`), а то, что одна и та же реальная компания записана десятками разных строк (5756 уникальных `company_name_raw` на ~1400 реальных компаний). Нужно связать заявки со справочниками и друг с другом, без ложных склеек.

Соответствует US8 (дубли заявок), US9 (соответствие компании), US10 (соответствие сотрудника по email/телефону/ФИО), US11 (несколько вариантов в неоднозначных случаях), US12 (массовое применение однозначных) — `research/user-stories.md`.

## Планка качества

**Быстро и обобщаемо важнее максимальной точности.** Обязательна блокировка кандидатов — никаких попарных сравнений всех со всеми (`O(n²)` на 6800+ заявках заметно тормозит). Внутри блока — маленький явный набор весов (3–4 сигнала), не тонко настроенная модель. Средняя зона уверенности отдаётся человеку вместо угадывания любой ценой.

## Вход

- Заявки (после Milestone 3: с нормализованными полями — `normalized_email`, `normalized_phone`, `normalized_company_name`, `normalized_city`, ИНН как есть/очищенный от префикса).
- Справочник Компаний — все записи, с предвычисленными ключами: `inn` (только цифры), `email`, `phone` (последние 10 цифр), `normalizedName`.
- Справочник Сотрудников — аналогично (`email`, `phone`, `normalizedFio`).
- Сами заявки — для application-application дедупа (тот же набор ключей).

## Что делает

1. Строит блокирующие индексы `Map<ключ, recordId[]>` отдельно по: ИНН, email, последние 10 цифр телефона, `normalizedName + normalizedCity` — для Компаний, Сотрудников и самих Заявок.
2. Для каждой заявки собирает кандидатов **только из тех же бакетов** (не весь справочник), считает score:
   - точное совпадение ИНН → `+0.5`
   - точное совпадение email → `+0.3`
   - точное совпадение телефона (10 последних цифр) → `+0.3`
   - строковое сходство `normalizedName` (Jaro-Winkler или Левенштейн, нормализованный в 0..1) × `0.3`
   - совпадение города → `+0.1`
   - сумма ограничивается `1.0`
3. Раскладывает по трём корзинам: **авто** (`score >= config.thresholds.matchAuto`, дефолт «all» в preview) — в этом случае в вывод идёт **только лучший** кандидат; **ручной разбор** (лучший кандидат в диапазоне `config.thresholds.matchManualLow <= score < matchAuto`) — в этом случае в вывод идут **топ-`config.thresholds.matchTopK` кандидатов** (дефолт `matchTopK: 3`) одной записи, ранжированные по score, чтобы пользователь выбирал из нескольких вариантов, а не принимал/отклонял единственный (US11) — плюс неявный вариант «ни один из вариантов»; **не показываем** (лучший кандидат `< matchManualLow` — вариантов сопоставления нет вообще).
4. Для заявка↔заявка — кластеризует транзитивно через union-find (если A~B и B~C, то A/B/C — один `duplicate_group_id`), а не просто попарные связи.
5. Оборачивает результат в форму `Action` (`kind:"link"`) и передаёт в тот же preview-движок Milestone 4 — своей отдельной логики подтверждения нет.
6. **Не перетирает** уже проставленную ссылку без явного отдельного запроса пользователя «rematch» (проверяется до формирования `Action` — если `Заявка.Компания` уже не пусто, этот кандидат в список действий не попадает).

## Выход

### `solution/src/lib/match.js`

```js
// findCompanyMatches(applications, companies, config) -> MatchCandidate[]
// findEmployeeMatches(applications, employees, config) -> MatchCandidate[]   // те же сигналы (email/phone/ФИО), что и для компаний — не "best-effort"-заглушка, а тот же алгоритм на полях preferred_assignee_raw/requester_*
// findApplicationDuplicates(applications, config) -> { clusters: string[][], candidates: MatchCandidate[] }
```

Форма `MatchCandidate` (конкретизация `Action` из Milestone 4, `kind:"link"`). Для `bucket:"auto"` — один элемент на заявку; для `bucket:"manual"` — до `matchTopK` элементов на заявку с одинаковыми `recordId`+`field`, различающихся `to`/`optionIndex`/`score` (US11):

```js
{
  recordId: "app_0007",          // заявка
  table: "applications",
  field: "company_link",           // | "employee_link" | "duplicate_link"
  from: null,                       // текущая связь (обычно пусто)
  to: "cmp_0042",                    // id кандидата — конкретно этого варианта
  changed: true,
  confidence: 0.91,
  reason: "точное совпадение ИНН + сходство названия 0.78",
  kind: "link",
  // + служебные поля только для этого модуля, не идущие в общий Action-конверт:
  bucket: "auto" | "manual",
  optionIndex: 1,                    // 1..matchTopK — порядковый номер варианта среди кандидатов ЭТОЙ заявки (для bucket:"auto" всегда 1)
  signals: { inn: true, email: false, phone: false, nameSim: 0.78, city: true }
}
```

Для `duplicate_group_id` дополнительно пишется текстовое значение (общий id кластера), не только Link.

`matchTopK` — новое поле `CopilotConfig.thresholds` (дефолт `3`), заводится в Milestone 2 вместе с `matchAuto`/`matchManualLow`.

## Критерий готовности

- На локальном seed (`local-seed.json`) распределение авто/ручных/none не вырождено (не 100% в одну корзину) — проверяется простым счётчиком в тесте.
- Полный проход по 6800 заявкам в mock-режиме укладывается в единицы секунд (не минуты) — проверка того, что блокировка реально работает, а не деградировала в `O(n²)`.
- Повторный запуск на уже связанных заявках не предлагает их заново (см. пункт 6 выше).
- Заявка с несколькими кандидатами в диапазоне «ручной разбор» возвращает `optionIndex: 1..N` (N ≤ `matchTopK`), а не единственный вариант — иначе тест на US11 не проходит.

## Демонстрация (обязательный шаг перед переходом к следующему milestone)

Прогон на подвыборке с заведомо «грязными» дублями компаний (см. примеры в `../PLAN.md#данные`): видно авто-группу связей и отдельно сгруппированную ручную группу (`12a`/`12b`/`12c` — несколько вариантов компании на одну заявку), выбираем вариант текстом, видно проставленную связь в дампе «Заявки».
