# Milestone C — таблицы и разовый импорт в реальной MWS

Статус: **реальная MWS, когда появится доступ**. После Milestone A/B.

## Зачем

Разложить `dev-sample.csv` по реальной структуре из `../PLAN.md#целевая-структура-данных-в-mws-tables`, чтобы дальше был реальный материал для Milestone D.

## Вход

- Раздатое пространство MWS Tables с подтверждённым (Milestone A) поведением API.
- `data/raw/dev-sample.csv`.
- `solution/src/setup/seed.js` — та же логика деления по `record_type`, что и в `devtools/seed.js` (Milestone 1), но пишущая через `createRecordsAsync` в реальные датасеты, а не в JSON.

## Что делает

1. Вручную (через UI MWS, без кода) создаёт 8 датасетов и все поля по схеме из `../PLAN.md#целевая-структура-данных-в-mws-tables`, включая типы `Two-way Link`/`One-way Link`/`Lookup` — с учётом точной формы `property`, найденной в Milestone A.
2. Импортирует `dev-sample.csv` нативным CSV-импортом MWS Tables в один staging-датасет (весь файл как есть, 82 колонки).
3. Запускает `setup/seed.js` (Script Widget на staging-датасете или отдельный разовый скрипт) — читает staging, ветвится по `record_type`, батчами создаёт записи в 5 целевых таблицах: в «Заявки» — только `*_raw` поля (без нормализации — это первый прогон основного виджета сделает сам).

## Выход

- 8 реально существующих датасетов в пространстве, с полями по схеме.
- Заполненные Компании (1400), Сотрудники (240), Шаблоны задач (360), Задачи (1200, сид из `EXISTING_TASK`), Проекты (заглушки по уникальным `PRJ-EX-DEV-*`), Заявки (6800, только `*_raw`).
- Staging-датасет можно удалить после сверки (не часть постоянной структуры).

## Критерий готовности

- Количество записей в каждой из 5 целевых таблиц точно совпадает с профилем `data/README.md` (6800/1400/240/360/1200).
- Ни одна запись «Заявки» не имеет заполненных `normalized_*`/`suggested_*`/`readiness_status` на этом этапе — это принципиально пусто до первого запуска основного виджета (иначе Milestone D не сможет продемонстрировать честный «было → стало»).
