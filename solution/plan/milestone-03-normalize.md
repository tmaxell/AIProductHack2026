# Milestone 3 — нормализация

Статус: локально, чистые функции без зависимости от SDK.

## Зачем

Заявки приходят в разных форматах (регистр, пробелы, ё/е, форматы дат/телефонов/бюджета). Нужно привести их к сравнимому виду, не теряя исходное значение, и показать пользователю, что и почему предлагается изменить.

## Планка качества

**Быстрый и универсальный набор правил важнее точности.** Каждая функция — чистая, разбирает **класс формата** (регэксп/паттерн), а не список конкретных строк из `dev-sample.csv` (см. `../PLAN.md#данные-datarawdev-samplecsv`). Не покрытый правилом вход не «дотягивается» спецкейсом — остаётся с низким `confidence` и уходит в ручной разбор через Milestone 4, а не блокирует пайплайн.

## Вход

Каждая функция получает **одно сырое значение** (строка или `null`/пусто) плюс, где нужно, **контекст, собранный в рантайме из справочников этого же прогона** (никогда не хардкод):

| Функция | Вход (значение) | Вход (контекст) |
|---|---|---|
| `normalizeEmail(raw)` | `" Info @ Company.ru "`, `"mailto:x@y.z"` | — |
| `normalizePhone(raw)` | `"8 (925) 952-11-02"`, `"+7(925)9521102"`, `"9098578150"` | — |
| `normalizeDate(raw)` | `"19/07/26"`, `"08.08.2026 18:27"`, `"11 декабря 2026"`, ISO | — |
| `normalizeDuration(raw)` | `"13 нед."`, `"P36D"`, `"104 дней"`, `"1 дн."` | — |
| `normalizeBudget(rawAmount, rawCurrency)` | `"1 967 000"`, `"2,08 млн"`, `"RUB 991000"`, `"4081 тыс."` | — |
| `normalizeCity(raw, knownCities)` | `"Г Екатеринбург"`, `"Члб"`, `"tomsk"` | `knownCities: string[]` — все `city`/`aliases` из справочника Компаний **этого прогона** |
| `normalizeCompanyName(raw)` | `"ооо «орбита логистика»"`, `"  Most Profil  "` | — (снятие орг.-правовой формы — фиксированный список ООО/АО/ИП/ЗАО/ПАО и т.п., общее доменное знание, не из CSV) |
| `normalizeFio(raw)` | `"Сидорова К.М."`, `"Николаев Максим"`, `"КОВАЛЁВА ВАЛЕРИЯ АЛЕКСЕЕВНА"` | — |
| `normalizeWhitespace(raw)` | любая строка | — |
| `normalizeYoAndCase(raw)` | любая строка (используется как ключ сравнения, не для отображения) | — |

## Единый контракт возврата

Каждая `normalizeX` возвращает:

```js
{
  value: any,        // предложенное нормализованное значение (или исходное, если ничего не меняем)
  changed: boolean,   // value !== raw (после тримминга/сравнения)
  confidence: number, // 0..1 — насколько уверены в преобразовании
  reason: string       // короткое объяснение для preview, например "lowercase + trim + strip mailto:"
}
```

Если формат не распознан вообще (например, дата в невиданном формате) — `{ value: null, changed: false, confidence: 0, reason: "unrecognized format" }`, это НЕ ошибка выполнения, просто идёт в ручной разбор.

## Выход

### `solution/src/lib/normalize.js`

Экспортирует все `normalizeX` функции по отдельности (для юнит-тестов, Milestone 11) плюс агрегатор:

```js
// buildNormalizationSuggestions(applications: RawApplicationRecord[], config: CopilotConfig, runtimeContext: {knownCities: string[]}) -> NormalizationSuggestion[]
```

Форма `NormalizationSuggestion` (это конкретный подвид общей формы `Action`, см. [`milestone-04-preview-engine.md`](milestone-04-preview-engine.md#сквозная-форма-action)):

```js
{
  recordId: "app_0001",
  table: "applications",
  field: "normalized_email",        // куда пишем при подтверждении
  from: null,                        // ТЕКУЩЕЕ значение normalized_email (пусто до первого прогона) — по нему определяется идемпотентность, см. Milestone 4
  displayFrom: " Info @ Company.ru ", // сырое значение-источник — только для колонки "Было" в preview
  to: "info@company.ru",
  changed: true,
  confidence: 0.95,
  reason: "email: lowercase + trim + strip mailto:",
  kind: "normalize"
}
```

Функция **не пишет ничего** в датасеты сама — только формирует список предложений, запись делает Milestone 4.

## Критерий готовности

- Юнит-тесты (Milestone 11) на все `normalizeX`, фикстуры — реальные строки из `dev-sample.csv` (см. примеры во входной таблице выше) плюс несколько «невиданных» вариантов для проверки graceful degradation.
- `buildNormalizationSuggestions` не предлагает изменения там, где значение уже нормализовано (идемпотентность на уровне функции — вызов дважды подряд на одних данных даёт `changed:false` на втором проходе).
- Ни одна функция не бросает исключение на пустом/`null`/мусорном входе.

## Демонстрация (обязательный шаг перед переходом к следующему milestone)

Т.к. полноценного preview ещё нет (это Milestone 4), демо-скрипт печатает через `console.table` топ-20 предложений `buildNormalizationSuggestions` на реальных данных `local-seed.json`: `recordId | field | from | to | changed | confidence | reason` — глазами видно, что разные форматы (даты/телефоны/бюджет/города) реально приводятся к одному виду.
