# Результаты тестирования

Живой журнал: одна секция на milestone, дописывается по мере прохождения плана (`solution/PLAN.md`). Для Milestones A–D (реальная MWS) это одновременно и итоговый отчёт, требуемый планом; для локальных Milestones 1–11 — промежуточная фиксация, чтобы не терять историю находок в переписке.

Все числа — с `data/raw/dev-sample.csv` через `solution/devtools/seed.js` (см. `data/README.md` про профиль выборки: 6800/1400/240/360/1200). Это **внутренняя** прикидка команды на dev-выборке, не официальная оценка организаторов (см. `data/AGENTS.md`).

## Milestone 1 — локальный mock-SDK и seed

**Дата:** 2026-09-04. **Команда:** `node solution/devtools/seed.js`.

- Счётчики записей точно совпали с профилем `data/README.md`: companies 1400, employees 240, templates 360, tasks 1200, applications 6800; плюс 417 заглушек легаси-проектов (уникальные `task_project_id`/`parent_project_raw`).
- Повторный запуск `seed.js` на том же `dev-sample.csv` — идентичный результат (кроме `generatedAt`) — воспроизводимость подтверждена.
- CSV-парсер корректно обработал многострочные quoted-поля (например `required_skills_raw` с переносами строк внутри значения).

**Статус:** пройден.

## Milestone 2 — мастер конфигурации

**Дата:** 2026-09-04. **Команды:** интерактивный прогон человеком (обнаружил проблему ниже) + скриптованный `run-local.js --answers demo-answers.json`.

- Полный мастер (8 таблиц, ~80 вопросов о полях) успешно проходит и сохраняет `CopilotConfig` в датасет «⚙️ Copilot Config».
- Повторный запуск без удаления кэша: «Конфигурация загружена из кэша — мастер настройки не запускается» — мастер не переспрашивает.
- `selectScope` спрашивается на **каждом** запуске (в отличие от мастера) — подтверждено.

**Найденная проблема (не баг кода, а UX):** при первом ручном тестировании пользователем не было понятно, что вводить в ответ на «ID таблицы» — в локальном mock это заранее сгенерированные `seed.js` строки (`dst_*`), а не что-то придуманное. **Исправление:** `run-local.js` теперь печатает шпаргалку со всеми ID таблиц перед тем, как мастер начнёт спрашивать (в интерактивном режиме без `--answers`).

**Статус:** пройден, с одной UX-доработкой.

## Milestone 3 — нормализация

**Дата:** 2026-09-04. **Проверено:** через полный прогон (Milestone 3+4 вместе, т.к. Milestone 3 сама по себе ничего не пишет).

- Полный прогон на всех 6800 заявках: **53 965** предложений нормализации, из них **53 527** авто-применено (confidence ≥ 0.5), **438** ушло в ручной разбор (в основном — короткие кириллические сокращения городов типа «Члб»/«Нск», confidence 0.4).
- Визуально проверены реальные трансформации на смешанных форматах: email (`mailto:`/пробелы/регистр), телефон (4+ формата → `+7XXXXXXXXXX`), даты (ISO/`дд.мм.гггг`/русские месяцы → ISO), бюджет (`1 967 000`/`2,08 млн`/`RUB 991000`/`4081 тыс.` → число + код валюты), город (алиасы из справочника компаний в рантайме), название компании (снятие орг.-правовой формы), ФИО (регистр + разбиение на части).
- Юнит-тесты на отдельные функции (`node --test`) — ещё не написаны, это Milestone 11.

**Статус:** пройден (сквозным прогоном); формальные юнит-тесты — отдельным пунктом в Milestone 11.

## Milestone 4 — движок preview/apply

**Дата:** 2026-09-04. **Команды:** `run-local.js` на 5/15/20/6800 заявках, скриптованный режим.

- Авто-группа (батч, дефолт `all`) и ручная группа (буквенные варианты `12a`/`12b`) корректно разделяются и печатаются раздельно.
- **Идемпотентность подтверждена на всех 6800 заявках:** прогон 1 → 53 527 применено / 438 пропущено; прогон 2 на результате прогона 1 (без изменения входа) → **0** применено / 438 пропущено (нерешённые неоднозначности корректно всплывают снова, применённое — не предлагается повторно).
- Производительность: полный прогон на 6800 заявках — **~0.5 с** (idempotent повтор — ~0.2 с). Соответствует планке «быстро» из Milestones 3/5 плана.
- Батч записи — один `updateRecordsAsync` на таблицу за прогон, а не по вызову на запись.

**Найденный и исправленный баг (идемпотентность):** изначально `Action.from` был сырым (`*_raw`) значением, из-за чего `from === to` никогда не выполнялось (raw-поля не перезаписываются) — предложения повторялись на каждом прогоне бесконечно. Исправлено: `from` = текущее значение поля-назначения (`normalized_*`), сырое значение вынесено в отдельное `displayFrom` только для отображения колонки «Было». План (`milestone-03/04.md`) обновлён вслед за кодом.

**Найденный и исправленный баг (UX ввода):** ошибка формата ответа (опечатка) роняла весь прогон целиком. Исправлено: `askUntilValid` — переспрашивает вопрос при ошибке разбора вместо падения. Заодно закрыта соседняя дыра: несуществующая буква варианта (например `12z` при вариантах только `a`/`b`) раньше молча игнорировалась без единого предупреждения — теперь явная ошибка с ретраем (`resolveGroupSelections`).

**Статус:** пройден, два бага найдены и исправлены в процессе.

## Автоматический отчёт по прогону (доработка devtools, не отдельный milestone)

**Дата:** 2026-09-04. Каждый вызов `run-local.js` теперь сам пишет `solution/devtools/reports/run-<таймстамп>.{md,json}` (не перезаписывается, история прогонов копится): конфигурация запуска, разбивка применённых/пропущённых изменений по каждому `normalized_*`-полю, причины пропуска (`already-applied`/`rejected-by-user`/`unresolved-ambiguous`/`other-option-chosen` — тегируются в `preview.js`), примеры «было→стало» по 3 на поле, плюс полный JSON без сокращений рядом. Папка закоммичена с `README.md`-политикой, сами отчёты — в `.gitignore` (генерируемый мусор per-run).

**Найденный и исправленный баг (нормализация ФИО), обнаружен прямо в примерах отчёта:** `titleCaseToken` не распознавал слитные двойные инициалы («Ю.Д.», «К.М.») как единый токен-инициал — под общую ветку («первая буква вверх, остальное вниз») попадало «Ю.Д.» → «Ю.д.» (второй инициал терял регистр). Исправлено: токен вида `(буква.)+` целиком распознаётся как инициалы и переводится в верхний регистр целиком. После фикса число авто-применённых нормализаций на полном прогоне закономерно снизилось (53527 → 52746) — это не потеря функциональности, а исчезновение ложных «исправлений» уже корректных значений. Идемпотентность и производительность не пострадали (повторный прогон — по-прежнему 0 применений, ~0.5с на 6800 заявок).

**Найденный и исправленный баг (честность `reason`), обнаружен пользователем при чтении JSON-отчёта:** `normalizeEmail` (и ещё 4 функции — `normalizePhone`, `normalizeBudget`, `normalizeCompanyName`, `normalizeFio`) возвращали **статический** текст причины на всю функцию независимо от того, что реально произошло с конкретным значением — например `"lowercase + trim + снят mailto:"` печаталось и тогда, когда в значении не было никакого `mailto:`, просто убрались пробелы по краям. Это подрывает доверие к объяснению рекомендации (кейс явно требует «причину предложения»). Исправлено во всех 5 функциях: `reason` теперь собирается из шагов, которые реально что-то поменяли в конкретном значении (например `"убраны пробелы по краям"`, `"снят префикс mailto:"`, `"нижний регистр"` — только те, что применились, через ` + `). Полный регресс на 6800 заявках после фикса: те же 52746 применено / 438 пропущено, идемпотентность и скорость не пострадали.

## Как повторить эти прогоны самостоятельно

```bash
node solution/devtools/seed.js
node solution/devtools/run-local.js --answers solution/devtools/fixtures/demo-answers.json
node solution/devtools/run-local.js --seed data/derived/local-run-result.json --answers solution/devtools/fixtures/demo-answers-run2.json
```
Второй файл ответов (`demo-answers-run2.json`) отличается от первого отсутствием ответа на вопрос авто-группы — она пуста на повторном прогоне, если всё уже применено.
