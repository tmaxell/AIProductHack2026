# Non-Functional Requirements — Project Launch Copilot

## 1. UX и прозрачность
- Все массовые изменения должны быть доступны в preview до применения.
- Пользователь должен видеть причину и уровень уверенности для каждой рекомендации.
- Неоднозначные случаи не должны изменяться автоматически.
- Интерфейс должен быть понятен менеджеру проекта без знания JavaScript.

## 2. Идемпотентность
- Повторный запуск на тех же данных не должен создавать повторные связи.
- Повторный запуск не должен повторно создавать уже созданные задачи.
- Уже применённые исправления не должны снова показываться как новые без изменения данных.
- Система должна поддерживать безопасную поэтапную дообработку заявок.

## 3. Конфигурируемость
- Решение не должно быть жёстко привязано к конкретным field ID.
- Пользователь должен иметь возможность выбирать поля и справочники при запуске.
- Конфигурация внешнего API, если используется, должна задаваться отдельно.

## 4. Безопасность
- Секреты и токены не должны храниться в исходном коде.
- Данные не должны отправляться во внешний API без явного действия пользователя.
- Ошибки интеграции и вызовов должны обрабатываться явно и показываться пользователю.

## 5. Надёжность
- Ошибки применения изменений должны быть локализованы и не приводить к потере данных.
- Исходные записи не должны удаляться.
- Решение должно корректно работать без внешнего LLM.

## 6. Масштаб MVP
- Решение должно быть оптимизировано под тестовый и демонстрационный сценарий.
- Промышленная отказоустойчивость и обработка миллионов записей не являются целями MVP.

## 7. Explainability
- Для рекомендаций по matching и классификации должна быть доступна интерпретируемая причина.
- Пользователь должен понимать, почему система предлагает конкретное изменение или связь.
