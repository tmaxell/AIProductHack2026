# План расширенных функций и целевой архитектуры

Статус: **согласованный план; пункт 1 раздела 3 реализован 2026-09-06**.

Документ описывает развитие нового локального веб-приложения в
`solution/webapp/`. Он не меняет baseline из `docs/core/PROJECT.md`:
подтверждённые требования кейса отделены от продуктовых и архитектурных
гипотез.

## 1. Исходное состояние и границы

Подтверждено по репозиторию:

- frontend остаётся статическим HTML/CSS/JavaScript рядом с
  контейнеризированным backend на TypeScript/Fastify; после PR #6 расширенный
  демонстрационный поток временно использует локальный движок;
- реализованы показ тестовых записей, детерминированная нормализация,
  сопоставление компаний, поиск дублей, отчёт `было → стало`, выборочное
  применение и откат в памяти страницы;
- импорт, граф связей и реальная LLM-интеграция пока не реализованы;
- полный сценарий обязан работать без LLM;
- массовые изменения требуют preview и подтверждения, а повторный запуск не должен создавать дубли;
- данные могут отправляться во внешний API только после явного действия пользователя.

Целевое правило остаётся прежним: доменная логика размещается в backend, а
frontend использует HTTP-контракты. Скопированные в PR #6 `engine.js` и
`launch.js` — осознанный временный долг: они остаются для подсказок сотрудников,
классификации и плана задач, но сохранение и публикация уже идут только через
Change Set API.

## 2. Продуктовый принцип: набор изменений

Все предложения помощника объединяются сущностью **Change Set — набор изменений**. Один Change Set может включать:

- исправления значений;
- создание и изменение связей;
- результаты импорта;
- будущие проекты и задачи;
- пояснения и рекомендации AI;
- решения пользователя по отдельным действиям.

Для каждого действия фиксируются:

- источник: правило, импорт, AI или пользователь;
- сущность и поле;
- значение `было → станет`;
- причина;
- confidence, если он вычисляется;
- статус решения пользователя;
- результат применения или ошибка.

Change Set становится единым контрактом между frontend и backend. Frontend показывает и редактирует предложение, backend анализирует, валидирует и применяет подтверждённые действия.

## 3. Версионирование и публикация

Статус реализации: выполнено. ADR, схема хранения и ограничения находятся в
`solution/webapp/docs/adr/0001-persistent-change-set-versions.md`. SQLite
подключён через persistent Docker volume; API и UI покрывают историю, diff,
решения, публикацию, конфликты, discard и компенсирующий rollback.

### 3.1. Пользовательский сценарий

1. Помощник анализирует выбранные данные и создаёт `Draft #1`.
2. Пользователь просматривает diff, принимает, отклоняет или редактирует действия.
3. Повторный анализ создаёт новую версию, не перезаписывая предыдущую.
4. Пользователь может сравнить версии и продолжить работу с выбранным draft.
5. Публикация применяет только подтверждённые действия.
6. Откат опубликованной версии создаёт новый draft с обратными действиями и также требует preview.

Минимальная модель состояний:

```text
draft → published → superseded
   └→ discarded

published → rollback draft → published
```

### 3.2. Правила целостности

- опубликованная версия неизменяема;
- изменение опубликованного результата создаёт новый draft;
- Change Set хранит базовую ревизию или fingerprint исходных данных;
- если исходные данные изменились после анализа, публикация блокируется конфликтом;
- откат не удаляет историю и не восстанавливает всё пространство целиком;
- повторная публикация одного Change Set идемпотентна;
- частично выполненный Change Set сохраняет результат каждого действия и допускает безопасный повтор.

### 3.3. Рыночный паттерн

Airtable Interface Designer автоматически сохраняет правки как draft и делает их видимыми пользователям после Publish. При этом Airtable не поддерживает восстановление отдельной ранее опубликованной версии интерфейса: используются дубликаты или snapshot всей базы. Для Project Launch Copilot целесообразно сохранить понятную модель `draft/published`, но добавить собственную неизменяемую историю Change Set и компенсирующий rollback.

## 4. Интеллектуальное объяснение через Groq

LLM используется как дополнительный слой объяснения и анализа, но не как источник непосредственных записей в MWS Tables.

### 4.1. Первая версия функции

- объяснить выбранные изменения простым языком;
- выделить риски и противоречия в структуре проекта;
- объяснить предложенную связь или неоднозначный matching;
- сформулировать вопросы пользователю;
- предложить следующие действия без автоматического применения.

Структурированный ответ провайдера:

```text
summary
evidence[]
risks[]
openQuestions[]
recommendedActions[]
```

### 4.2. Guardrails

- перед отправкой показывать пользователю состав передаваемых полей;
- выполнять вызов только по явному действию пользователя;
- минимизировать и при необходимости маскировать персональные данные;
- не передавать в prompt секреты, внутренние инструкции и не относящиеся к вопросу записи;
- не давать модели права публиковать Change Set или выполнять произвольные инструменты;
- валидировать ответ по JSON Schema;
- сохранять модель и версию prompt рядом с результатом;
- поддерживать timeout, ограниченное число повторов и backoff для `429` и `5xx`;
- при любой ошибке Groq сохранять работоспособность детерминированного сценария.

Groq поддерживает Structured Outputs по JSON Schema, но строгий режим доступен не для всех моделей. Поэтому endpoint, модель, режим structured output и лимиты должны задаваться конфигурацией, а не быть зашиты в доменную логику.

### 4.3. Работа с ключом

Реальный Groq API не должен вызываться из браузера с постоянным секретом. Официальные рекомендации Groq запрещают встраивать ключ во frontend и предлагают доверенный backend proxy.

Backend уже существует, поэтому будущий Groq-провайдер подключается только за
внутренним endpoint. Groq key хранится в переменных окружения backend и не
возвращается клиенту. До реализации интеграции допустим только
`MockExplanationProvider` без сетевого вызова.

## 5. Настройка связей и граф

Нужно разделить два представления:

- **граф схемы** — таблицы, поля и типы связей;
- **граф проекта** — заявка, компания, проект, задачи и исполнители.

Первой реализуется схема пространства, поскольку она нужна для настройки и проверки дальнейших действий.

### 5.1. Узел графа

- идентификатор и название таблицы;
- primary field;
- количество записей;
- статус конфигурации;
- предупреждения целостности.

### 5.2. Ребро графа

- исходная таблица и поле;
- целевая таблица;
- `OneWayLink` или `TwoWayLink`;
- одиночная или множественная связь;
- ограничение выбранным view;
- связанные Lookup-поля;
- состояние: существующая связь, предложение или ошибка.

### 5.3. Поведение

- фильтрация существующих, предлагаемых и ошибочных связей;
- фокус на выбранной таблице и подсветка зависимостей;
- поиск потерянных ссылок и отсутствующих обратных полей;
- мастер создания связи;
- добавление предложения связи в draft;
- preview затрагиваемых полей и записей;
- применение только после подтверждения.

`TwoWayLink` создаёт связанную пару полей, `OneWayLink` существует только в исходной таблице, а Lookup вычисляется поверх Link и не должен записываться напрямую. Backend должен учитывать это при формировании команд.

Базовая демонстрационная схема:

```text
Заявки → Компании
Заявки → Проекты
Проекты ↔ Задачи
Задачи → Сотрудники
Проекты → Шаблоны задач
```

## 6. Импорт Excel, CSV и Jira

Основа функции — единый импортный конвейер, а не отдельная несвязанная реализация для каждого источника:

```text
Файл → определение формата → preview → mapping → валидация
     → поиск существующих записей → Change Set draft → публикация
```

### 6.1. Очередь адаптеров

1. Generic CSV.
2. Jira CSV как готовый профиль mapping.
3. XLSX.
4. JSON.
5. Прямой Jira API или webhook — только при отдельном подтверждении scope.

### 6.2. Стартовый Jira mapping

| Jira | Поле помощника |
|---|---|
| Issue key | `external_id` |
| Summary | название проекта или задачи |
| Description | описание |
| Issue Type | тип |
| Status | статус |
| Priority | приоритет |
| Assignee | исполнитель |
| Reporter | инициатор |
| Parent / Epic | родительская связь |
| Created / Updated / Due date | даты |
| Labels / Components | множественные значения |

### 6.3. Обязательное поведение

- пользователь подтверждает mapping;
- неизвестные колонки не теряются молча и видны в preview;
- повторяющиеся заголовки Jira обрабатываются как многозначные поля;
- preview разделяет создаваемые, обновляемые, пропускаемые и ошибочные записи;
- вложения на первом этапе сохраняются только как ссылки;
- mapping можно сохранить как профиль;
- ключ идемпотентности: `source_system + source_instance + external_id`;
- повторный импорт того же файла создаёт ноль дублей;
- импорт формирует draft и ничего не публикует автоматически.

Jira Cloud экспортирует результаты в UTF-8 CSV, в том числе вариант `all fields`; комментарии и другие множественные значения могут находиться в повторяющихся колонках. MWS Tables официально поддерживает Excel и CSV, поэтому Jira CSV укладывается в текущий scope без боевой интеграции с Jira.

## 7. Целевая техническая архитектура

Введённый backend убирает внешние интеграции и секреты из браузера, даёт
будущую транзакционную границу для публикации Change Set и единое место для
импорта, matching и LLM. Персистентность и транзакции публикации ещё не
реализованы.

### 7.1. Границы компонентов

```text
Frontend
  ├─ таблица и выбор scope
  ├─ review/diff и версии
  ├─ граф связей
  └─ мастера импорта и публикации
          │ HTTP/JSON
          ▼
Backend API
  ├─ application: сценарии и транзакции
  ├─ domain: Change Set, правила, статусы, конфликты
  ├─ import: CSV/Jira/XLSX adapters
  ├─ matching: детерминированные правила и confidence
  ├─ integrations: MWS Tables и Groq adapters
  └─ persistence: версии, actions, run log, mappings
          │
          ├─ MWS Tables
          └─ Groq
```

### 7.2. Архитектурные правила

- доменная логика не зависит от HTTP, DOM, Groq SDK и конкретных ID MWS;
- frontend не повторяет серверные правила и считает backend источником истины для публикации;
- внешние сервисы подключаются через узкие adapter-интерфейсы;
- DTO API отделены от доменных сущностей;
- операции публикации имеют idempotency key;
- каждая запись во внешний сервис возвращает нормализованный результат по отдельному action;
- конфигурация и секреты поступают через окружение;
- логи структурированы, но не содержат секретов и сырых персональных данных;
- ошибки имеют стабильный код и безопасное пользовательское сообщение;
- миграции данных версионируются;
- health/readiness endpoints проверяют процесс отдельно от внешних зависимостей;
- API документируется OpenAPI после фиксации первого контракта.

### 7.3. Docker

Целевой локальный запуск должен быть воспроизводимым через Docker Compose:

- отдельный контейнер backend;
- frontend либо раздаётся отдельным web-контейнером, либо в dev-режиме запускается существующим способом;
- локальное хранилище выбирается только после уточнения требований к сохранению версий;
- секреты передаются через некоммитящийся env-файл;
- контейнер запускается от непривилегированного пользователя;
- добавляются healthcheck, ограниченный build context и `.dockerignore`;
- production image собирается multi-stage и не содержит dev-зависимостей;
- наружу публикуются только необходимые порты.

Для первой итерации уже выбраны TypeScript, Fastify и TypeBox; приложение
запускается через Docker Compose. Постоянное хранилище ещё не выбрано. Перед
его добавлением нужен короткий ADR со сравнением вариантов и миграционной
стратегией.

## 9. Критерии готовности

### Версии

- опубликованную версию нельзя незаметно изменить;
- rollback всегда проходит через новый preview;
- конфликт исходных данных обнаруживается до публикации;
- повторный запрос с тем же idempotency key не создаёт повторных действий.

### Связи

- граф различает One-way, Two-way и Lookup;
- направление, кратность и view restriction отображаются корректно;
- Lookup никогда не предлагается как записываемое поле;
- массовое создание связей выполняется только после preview.

### Импорт

- Jira fixture корректно проходит mapping;
- немаппированные и повторяющиеся колонки видны пользователю;
- повторный импорт создаёт ноль дублей;
- частичная ошибка не скрывает результаты остальных строк.

### Groq

- без Groq весь базовый сценарий работает;
- секрет отсутствует в frontend, репозитории и пользовательских логах;
- пользователь видит состав отправляемых данных;
- невалидный ответ модели не превращается в action;
- AI не публикует изменения самостоятельно.

### Поставка

- локальный запуск воспроизводим по одной документированной команде;
- backend и domain покрыты unit-тестами, критические сценарии — интеграционными тестами;
- Docker image проходит healthcheck;
- повторный полный сценарий не создаёт повторные связи и задачи.

## 10. Оставшиеся архитектурные решения

- временное или постоянное хранилище Change Set;
- источник метаданных пространства для графа;
- допустимость отдельного backend в условиях финальной поставки Widget Script;
- способ аутентификации frontend → backend в демонстрации;
- нужен ли реальный MWS adapter в первой итерации или достаточно mock-контракта;
- допустимый состав данных для Groq и правила маскирования.

До получения ответов эти пункты считаются архитектурными гипотезами, а не
подтверждёнными требованиями. Выбранный стек backend и Docker-каркас уже
зафиксированы реализацией в `solution/webapp/`.
